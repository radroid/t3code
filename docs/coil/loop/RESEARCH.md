# autoresume

## Summary

The fork's auto-resume feature is a self-contained subsystem under apps/server/src/coil/autoResume/ that self-starts as an Effect layer (`Layer.effectDiscard(makeSupervisor)`) and touches only three lines of upstream code (server.ts import + `Layer.provideMerge(CoilLayerLive)` + one route-list entry). Detection subscribes to `ProviderService.streamEvents` (a `Stream.Stream<ProviderRuntimeEvent>`) and matches `event.type === "account.rate-limits.updated"` with `event.provider === "claudeAgent"`, classifies the payload with a pure `classifyRateLimit`, and schedules a pending resume in a durable JSON store. A second scoped fiber polls every `pollMs`, re-reads a FRESH `ProjectionSnapshotQuery.getSnapshot()` per due item, re-runs every guard, then submits a follow-up turn via `engine.dispatch({ type: "thread.turn.start", ... })` with CommandId/MessageId prefixed `coil-auto-resume:` and text resolved from per-thread override → `<workspaceRoot>/.t3x/resume-prompt.md` → the literal `"continue"`. Guards live in pure guards.ts (thread-gone / not-claude / progressing / awaiting-input via a mirrored `hasOpenBlockingRequest` / user-took-over / thread-advanced) plus a 24h fire cap checked at BOTH schedule time (decide.ts) and fire time (Reactor.ts). Config is env-only (`T3X_AUTO_RESUME_*`, no settings schema, no contracts change), state is a single versioned JSON file written atomically inside a `SynchronizedRef` critical section, and the per-thread on/off + prompt override is exposed through a raw HTTP route `/api/coil/auto-resume` registered via `Layer.unwrap` so the store requirement never leaks into upstream's `makeRoutesLayer` type. The WebPush reactor is the same layer/fiber shape but taps `OrchestrationEngineService.streamDomainEvents` (domain events, not provider runtime events), filters with a denylist instead of an allowlist, and uses narrow per-thread shell queries instead of the heavy full snapshot.

## Open questions

- There is NO snooze guard anywhere: `threadIsGone` covers deletedAt / archivedAt / settledOverride === "settled" only, even though `thread.snooze`/`thread.unsnooze` commands exist in contracts (orchestration.ts:776-777). A loop supervisor probably wants to treat a snoozed thread as paused — decide deliberately rather than by copying `threadIsGone`.
- `processDue` runs due items sequentially (`Effect.forEach(..., { discard: true })`, no concurrency, no per-item timeout) and each item re-reads the FULL `getSnapshot()`. With many supervised threads per tick this is O(threads) full-snapshot hydrations.
- The wake loop is `processDue.pipe(Effect.delay(pollMs), Effect.forever)`, so the delay applies before every iteration and the first pass happens pollMs after boot. If a supervisor needs an immediate first pass, that ordering must change.
- `resolveConfig()` reads `process.env` once at layer construction; there is no runtime reconfiguration path. A supervisor with a tunable cadence would need a restart or a store-backed setting like `overridePrompt`.
- The store is keyed by threadId only — no project or global scope and no cross-thread coordination. A supervisor needing a global budget ('at most N autonomous turns in flight across all threads') has no prior art; `countFiredSince` is per-thread.
- `fireOne` reserves the attempt via `recordFired` BEFORE dispatch, so a dispatch failure permanently consumes a budget slot. With a small supervisor budget that trade-off (no tight-loop retry vs. lost slots) may need revisiting.
- Nothing verifies the dispatched turn actually started — the reactor fires and forgets (`Effect.catchCause` → logWarning). A supervisor that must confirm the follow-up turn ran would need a new post-dispatch observation path; none exists in this prior art.
- `AutoResumeState.version` is `Schema.Literal(1)` with no migration code path: a future version bump makes old files fail decode, which the boot path silently turns into EMPTY_STATE. Any new store should decide up front whether it needs a real upgrade path or the same additive `withDecodingDefaultKey` discipline.

# settings

## Summary

Settings in T3 Code are split in two: `ServerSettings` (server-authoritative, persisted as sparse JSON at `<stateDir>/settings.json`, read/written over WS-RPC) and `ClientSettingsSchema` (client-local, persisted to localStorage key `t3code:client-settings:v1` in the browser or a JSON file via Electron IPC on desktop). Both are flat `Schema.Struct`s where essentially every field is `X.pipe(Schema.withDecodingDefault(Effect.succeed(default)))`, and the defaults objects are literally `Schema.decodeSync(Schema)({})`. Each has a hand-maintained parallel `*Patch` struct of `Schema.optionalKey(...)` fields, so adding one setting means two edits in `packages/contracts/src/settings.ts`. # claude-adapter

## Summary

T3 Code drives Claude Code through the **Agent SDK** (`@anthropic-ai/claude-agent-sdk`, ^0.3.170), not a hand-spawned CLI and not ACP. `ClaudeAdapter.ts` calls the SDK's `query({prompt, options})` once per thread session in _streaming-input_ mode: `prompt` is an `AsyncIterable<SDKUserMessage>` fed from an Effect `Queue`, and `options.pathToClaudeCodeExecutable` points at the real `claude` binary, which the SDK spawns as a subprocess. Because `systemPrompt: {type:"preset", preset:"claude_code"}` and `settingSources: ["user","project","local"]` are set, the spawned CLI loads `~/.claude` + `.claude/` settings, so filesystem hooks, skills, agents and custom slash commands behave as in the terminal. A turn is one `sendTurn` -> `Queue.offer` of a user message; a `sendTurn` while a real turn is running is a **steer** (same `turnId`, no new turn boundary), and the turn is closed by the SDK's `result` message via `completeTurn`, which emits `turn.completed` and clears `turnState` unconditionally. That is the issue-38 root cause: the adapter tracks no outstanding-task set, swallows both `task_updated` (which carries `status` / `is_backgrounded`) and `background_tasks_changed`, and `SDKResultSuccess` carries no background-task field — so `task.progress`/`task.started`/`task.completed` events keep arriving after `turn.completed`, now with `turnId` omitted (persisted as `turnId: null`). `ProviderAdapterCapabilities` has exactly one flag (`sessionModelSwitch`); there is no `supportsSteering` and no `supportsBackgroundTasks`.

## Seam risks

- `apps/server/src/provider/Layers/ClaudeAdapter.ts` — The only place that knows a `task_started` has no matching `task_notification`. Gating `turn.completed` on outstanding tasks, or emitting a new pending-tasks signal, means editing a 3951-line upstream file that is the hottest provider file in the tree and is already cited four times in SEAMS.md.
  - _avoid:_ Do NOT gate turn completion in the adapter. Reconstruct the same state in a fork-owned reactor under apps/server/src/coil/: subscribe to `providerService.streamEvents` (a fresh PubSub subscription, zero seam) and maintain your own `Map<taskId, startedAt>` per threadId from `task.started` / `task.completed`. When `turn.completed` arrives with a non-empty outstanding set, you have the stall signal without touching upstream. If you must have `task_updated` / `background_tasks_changed`, prefer a Stop hook written into the CLI-visible settings (or the `launchArgs`/`extraArgs` escape hatch) over adding a switch case — the adapter's `message satisfies never` guard makes a case edit permanent maintenance.
- `apps/server/src/provider/Services/ProviderAdapter.ts` — Adding `supportsBackgroundTasks` / `supportsSteering` to `ProviderAdapterCapabilities` would widen an upstream interface, forcing an edit in all five adapters (Claude, Codex, Cursor, Grok, OpenCode) plus the registry mock — six new ledger rows.
  - _avoid:_ Keep the driver-kind allowlist pattern the fork already uses for steering (`apps/web/src/outbox/composerSteering.logic.ts`), but put it in a fork-owned server module and add a test that fails when a new `ProviderDriverKind` appears — the existing steer allowlist has no such tripwire, which SEAMS.md flags as a live hazard.
- `apps/server/src/orchestration/Layers/ProviderRuntimeIngestion.ts` — It owns the `turn.completed` -> `status: "ready"` / `activeTurnId: null` transition and the `turnId: null` on orphaned task activities, so a 'supervised / stalled' thread state looks like it belongs here.
  - _avoid:_ Do not change the projection. The stall is already derivable read-only: `projection_turns.completed_at` plus `task.*` activities with `turnId: null` arriving after it (exactly what issue 38 proposes). Compute it in a fork reactor and persist supervision state in a fork-owned JSON store under `config.stateDir`, mirroring `t3x-auto-resume.json` — auto-resume persists per-thread state with zero schema change.
- `packages/contracts/src/providerRuntime.ts and packages/contracts/src/orchestration.ts` — Surfacing subagent identity (`subagent_type`) or a 'pending tasks at completion' count would want new fields on `TaskStartedPayload` / `OrchestrationThreadActivity`.
  - _avoid:_ `OrchestrationThreadActivity.payload` is an open record and `thread.activity.append` accepts an arbitrary `kind` string — the auto-resume reactor writes `coil.auto-resume.*` activities this way with no contract change. Emit `t3x.supervisor.*` activities instead of extending the schemas. Note SEAMS.md's warning that `packages/contracts/src/settings.ts` is a _persisted_ schema and already a seam.
- `apps/web/src/components/ChatView.tsx and the sidebar components` — Issue 38's second half asks for pinned, visually distinct supervised threads in the sidebar — ChatView.tsx is the highest-risk row in the ledger (risk 11466, 63 upstream commits in 60 days).
  - _avoid:_ Mount a fork-owned overlay/badge as a sibling rather than editing ChatView internals — the fork already does this for `<AutoResumeOverlay>` in `apps/web/src/routes/_chat.$environmentId.$threadId.tsx` (+10/-6, risk 80) and `<NotificationCoordinator>` in `__root.tsx`. - `apps/server/src/coil/index.ts and apps/server/src/server.ts` — Any new server-side supervisor must be registered somewhere.
  - _avoid:_ This is the intended, already-paid seam: merge the new layer into `CoilLayerLive` (and routes into `CoilRoutesLive`). `server.ts` needs no further edit — it already has the one import and one `Layer.provideMerge`. It would have to be written into the CLI-visible `.claude/settings.json` for the thread's cwd (or the instance's `CLAUDE_CONFIG_DIR`), and the hook process would need a callback path into T3 — the `settingSources` wiring means T3 does not own that file. `options.hooks` (sdk.d.ts:1486) would give in-process callbacks but requires editing ClaudeAdapter's query-options block, which is a real seam.
- Does `query.backgroundTasks()` help or hurt? It _backgrounds_ foreground tasks (Ctrl+B semantics) rather than listing them, so calling it changes agent behaviour rather than just observing. There is no read-only 'list in-flight tasks' method on `ClaudeQueryRuntime` (ClaudeAdapter.ts:205-212).
- What is the intended interaction with the existing auto-resume supervisor? Issue 38 flags 'two mechanisms racing to revive the same thread'. Auto-resume fires only on `account.rate-limits.updated` with `status:"rejected"` (Reactor.ts:283-289), so the triggers look disjoint — but both dispatch `thread.turn.start` and both need `maxResumesPer24h`-style caps and the `settled`/`snoozed` guards in `guards.ts`.
- Should a stalled turn be re-prompted, or should the _turn_ simply not be marked completed until its tasks settle? The second is more correct but is squarely an upstream-file change; the first is fork-shaped but re-prompts a possibly-finished agent. Issue 38 explicitly notes the underlying mechanism 'may deserve its own bug report' — upstream fix vs fork workaround is still undecided.
- How do synthetic turns interact with a supervisor? A background subagent's assistant message auto-opens a synthetic turn (ClaudeAdapter.ts:2467-2506) which sets session status back to `running`. A naive 'idle for N minutes with no active turn' detector will see the thread flip running->ready repeatedly and may never fire, or may fire mid-synthetic-turn and have its message folded into the synthetic turn as a steer.
- Should a supervisor re-prompt use `thread.turn.start` (auto-resume's path) or an explicit steer? If a synthetic turn is open at re-prompt time, ClaudeAdapter closes it with `completeTurn(context, "completed")` first (ClaudeAdapter.ts:3736-3738) — worth confirming that does not corrupt supervised-run bookkeeping.

# orchestration

## Summary

t3code's orchestration is a CQRS/event-sourced core: a single serialized command bus (OrchestrationEngineService.dispatch) feeds a pure decider.ts that turns commands into OrchestrationEvents, which are appended to orchestration_events and fanned out to (a) an in-memory OrchestrationReadModel, (b) the SQLite ProjectionPipeline (projection_threads, projection_turns, projection_thread_activities, projection_thread_sessions), and (c) a hot streamDomainEvents PubSub that reactors subscribe to. Turn lifecycle lives entirely in projection_turns (state = pending|running|interrupted|completed|error, with requested_at/started_at/completed_at), and the authoritative turn-end signal is thread.session-set leaving the "running" status, not the last assistant message. Thread-level lifecycle is three orthogonal things stored as columns on projection_threads: archived_at, settled_override+settled_at, and snoozed_until+snoozed_at — there is no "pinned"; the closest thing is settledOverride "active" (a keep-active pin). Activities are NOT a discriminated union at the orchestration layer (kind is an open TrimmedNonEmptyString, payload is Schema.Unknown); the real union lives one layer down as ProviderRuntimeEvent. There is no cron/scheduler service anywhere on the server — every periodic job is a hand-rolled Effect.forkScoped + Effect.forever — and the fork already ships working prior art at apps/server/src/coil/autoResume/Reactor.ts that schedules and dispatches thread.turn.start on existing threads.

## Open questions

- What is the intended 'idle' trigger for the loop supervisor? There is no server-side idle timer today. ## Open questions

- Does a background subagent's assistant message actually leave a synthetic turn open indefinitely in practice? If yes, session.status is stuck at 'running' for exactly the issue-38 threads, and BOTH a phase-based ('completed' edge) and a status-guard-based ('not progressing') design fail. This is the single highest-value thing to confirm empirically: run an overnight Task-tool session with ClaudeAdapterLiveOptions.nativeEventLogPath set (ClaudeAdapter.ts:223) and check whether a `result` arrives after each background assistant message. Everything about the trigger design hangs on this.
- Which stream should the supervisor tap: providerService.streamEvents (runtime, carries raw.payload with subagent_type, no persistence lag, but only claudeAgent-shaped) or engine.streamDomainEvents (durable, provider-agnostic, but activity payloads are lossy — subagent_type is stripped at ProviderRuntimeIngestion.ts:495)? autoResume uses the former, webPush the latter. Tapping BOTH from one reactor is unprecedented in the fork.
- Does task.started always eventually pair with task.completed? The adapter emits task.completed only from `task_notification` (ClaudeAdapter.ts:2716). A task killed by session exit or process crash may never notify, so the open-task set needs a staleness TTL. No evidence in-tree either way; the NDJSON capture above would settle it.
- If the idle trigger is `now - shell.updatedAt > N`, what is N, and does it need to be per-thread configurable? The upstream precedent (sidebarAutoSettleAfterDays) is measured in DAYS; issue #38's symptom is 'silent for hours'. The autoResume config is env-only with no runtime reconfiguration path (config.ts:67-71 reads process.env once at layer construction).
- Should the supervisor fire when a synthetic turn is open? sendTurn force-completes a synthetic turn before starting a new one (ClaudeAdapter.ts:3736), which would emit a spurious turn.completed for work that was genuinely mid-flight. Unverified whether that corrupts turn bookkeeping.
- Should the supervisor add a snooze guard (auto-resume has none — guards.ts:100-104 checks only deletedAt/archivedAt/settledOverride==='settled') and should it refuse to clobber a 'keep-active' pin? decider.ts:829 unsettles for settledOverride !== null, so an unguarded supervisor turn silently destroys BOTH a settle and a keep-active pin.
- Is `apps/server/src/coil/loop/` the right home, or should the supervisor extend `autoResume/` to avoid two reactors racing to revive the same thread? Both dispatch thread.turn.start and both need the same guards + 24h caps, but their triggers are disjoint (rate-limit rejection vs idle-with-no-open-tasks). Nothing in-tree coordinates two fork reactors dispatching to the same thread.
- What is the target APP_STAGE_LABEL of the build the user actually runs? sidebarV2Enabled defaults to false in the schema (contracts/settings.ts:127) and is stage-overridden elsewhere; if the mount is AppSidebarLayout.tsx:203 this stops mattering (it covers both), but any v2-only design still needs the stage confirmed.
- Is there appetite to fix the fork's existing getSnapshot() OOM hazard (SEAMS.md:105, autoResume/Reactor.ts:155/182) in the same PR? The supervisor should use getThreadShellById from day one regardless, but the deferred reconciler swap is still open and a polling supervisor multiplies the exposure.
