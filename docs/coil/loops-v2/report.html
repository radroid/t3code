Loops, and the question nobody was awake to answer

A consolidated design for running a thread unattended — and, more importantly, for what you see when you come back to it. Six clickable prototypes, one backend recommendation, 137 test cases, and the three things I found that make the previous design out of date.

0 The short version

What I would build, and what I would not

Recommendation

Build a durable, T3-native loop reactor — a fork-owned supervisor that restarts a silent thread on an idle clock, bounded by a mandatory check-in budget and a wall-clock deadline, with state on disk so a 3am reboot loses nothing.

Make its user-facing surface a console, not a pill: when you open a loop you get a standing answer to "what do you need from me?", assembled from three independent sources so it stays useful even if the model never cooperates.

Ship a loop as a pinned thread (Direction A) — upstream already built pinning, so the sidebar costs nothing. Keep the Loops workspace (Direction C) as the phase-2 upgrade once there is more than one loop to look at.

The one thing I would push back on

You asked for a questionnaire page. It is the right idea and it is the centrepiece of this report — but the obvious way to build it is a trap, and it is worth knowing before you pick. Claude's AskUserQuestion already produces exactly the structured questions you want, natively, today. It also blocks the turn until a human answers. An agent that hits a real fork in the road at 01:00 and asks about it correctly stops working until 09:00 — which is the precise failure you are trying to eliminate.

So the console needs two channels, not one: blocking questions (which genuinely stop the run) and deferred blockers (which do not). The distinction is not a technicality — it is the product. See §3.

01 Evidence

The night this comes from

Everything below is downstream of one real run: thread 3a85bdd3, "Overnight TDD agent orchestration", 31 turns across seventeen hours.

Stall A Stall B Turn marked completed 00:19:19Z 07:40:44Z Background activity 1,358 more 61 more still arriving (until 00:52) (until 07:48) Then total silence 3h 31m 6h 50m Ended by human: "continue" human: "You stopped again"

Stall A's 1,358 orphaned activities were 715 task.progress, 57 task.started, 58 task.completed, 527 context-window.updated. Subagents kept working for 33 minutes inside a turn the server had already closed. In Stall B a task started twelve seconds before the turn closed.

Both turns reported state: completed with no error anywhere. The thread was not settled, snoozed, archived or rate-limited. Auto-resume was never involved and could not have been — it triggers on needs-input, and this thread never needed input.

The actual cost

All eighteen user messages that night were human. "Did you get started?" · "Any updates?" · "Are you still working?" · "Continuing?" · "I am going to bed now, ensure that your sub agents are not dying" · "You stopped again". The human was the loop, all night. That is the thing being replaced.

What upstream has since fixed — and what it has not

Upstream's ThreadBackgroundLiveness (in the fork since the 2026-08-08 sync) now maps the whole task.* lifecycle and surfaces it as a sidebar pill and a composer banner. That closes visibility: a stall is identifiable at a glance instead of requiring you to open the thread and read its timeline.

It does not close supervision. Every consumer of that signal is presentation — nothing re-prompts, nothing enqueues a turn, nothing acts. And its own module doc is explicit: "no persistence, no migration. After a server restart the registry is empty." On the night above it would have shown a "working" pill for 33 minutes and then gone quiet for 3h31m, exactly as before.

Durability and acting on the signal are the whole of what is left to build.

02 Re-measurement

Three things that moved under the old design

There is a 73k-word design at docs/coil/loop/DESIGN.md from a 4-design, 12-judgement panel. Most of it survives and I have reused it. Three of its load-bearing premises have expired.

1 · Upstream shipped pinning — two days after the design froze

da6e1a967 2026-08-04 feat(sidebar-v2): thread pinning for sidebar v2 (#5312) design frozen 2026-08-02 — two days earlier

pinnedAt is a real contract field. thread.pin / thread.unpin are dispatchable commands. There is a drag-reorderable pinned block that renders with no header. And the contract says outright: "A pin overrides the settled/snoozed lifecycle: while pinnedAt is set the thread renders in the pinned block and never classifies into a shelf."

The old design spent considerable effort rejecting a sidebar rail — including a proposed document.querySelector portal it correctly called out as laundering hidden dependencies. That rejection was right, and it is now moot: the thing it was avoiding building already exists, reachable through a command instead of a DOM hack.

Consequence

"A distinct thread type that pins to the top of the sidebar" — issue #38's proposal 2 — is now mostly an upstream feature. Arming a loop can just dispatch thread.pin.

2 · The sidebar is not a seam row, and that cuts both ways

Sidebar.tsx (3808 lines) and Sidebar.logic.ts appear nowhere in SEAMS.md. The fork does not touch the sidebar at all today. So modelling a loop as a pinned thread costs zero — and giving it bespoke rendering opens a new row in one of the hottest files upstream owns.

The sidebar also states a rule that decides this:

Sidebar.logic.ts

"Sidebar sort: static creation order, newest thread on top. Activity NEVER reorders the list — a row holds its position from open until settled, so the screen only moves at lifecycle transitions."

A loop that floats to the top because it is busy breaks that rule. A loop that pins does not — pinning is a lifecycle transition. That single sentence is why Direction A is idiomatic rather than a shortcut, and why any design that sorts loops by activity should be rejected outright.

3 · The settings mount in the old design no longer exists

BetaSettingsPanel.tsx is gone. Today's settings surface is seven route files and a closed SettingsPath union in settingsSearch.ts that drives both the nav and search. The old design's "+2 lines, risk 6" costing is void, and re-pricing it is one of the open decisions in §13.

03 The centrepiece

The console — a standing answer to "what do you need from me?"

Your ask, restated: at any time I open the chat there should be a page where I have a questionnaire ready to be answered, or the things that are a blocker and the human is needed for. This is that page.

The old design's user surface was a pill — Loop watching · 12m, Loop 2/6 · ends 07:00. That answers "is it alive". It does not answer "what is it stuck on and what do you want from me", which is the question you actually have at 9am.

P1 Loop Console Click the four scenarios along the top, and answer a question to watch the loop resume. Open standalone ↗

What to look at: the four scenarios along the top are the four ways a morning can go. Answering an option marks it resolved and — once the blocking ones are cleared — flips the loop back to Working, because answering is the resume. Note that "Stopped on these" and "Answer when you can" are visually distinct sections: that split is the whole design.

Why two channels, not one

AskUserQuestion is already a first-class concept. The Claude adapter intercepts it in canUseTool, emits a user-input.requested event carrying a structured payload, and the projection surfaces it as hasPendingUserInput — the indigo Awaiting Input you already see in the sidebar. The schema is exactly what a questionnaire needs:

UserInputQuestion = { id, header, question, options: [{ label, description }], multiSelect? } packages/contracts/src/providerRuntime.ts:444-464

And then, in the adapter:

// ClaudeAdapter.ts:3852 const answers = yield* Deferred.await(answersDeferred); // blocks until a human answers
The trap

A loop and a blocking question are in direct tension, and no tuning resolves it. Nudge a thread parked on a real question and you push past the human's decision. Don't nudge it and one question costs the whole night. The guard table is right to refuse — which means the fix has to be a different channel, not a different threshold.

So: a fork-owned MCP tool, raise_blocker, that records a question and returns immediately. The agent parks that branch of work and carries on with something else; the answer is delivered on a later check-in. Blocking questions still exist and still block — but they become the exception rather than the only option.

Why this is not the mistake the old design already rejected

The old panel rejected an agent-authored contract (its "BATON" design) because it "outsources the hardest judgement to the thing that just failed" and "degrades silently". A questionnaire is that idea coming back through a different door, so it has to answer the same objection. It does, for one structural reason:

Console sourceNeeds the model to cooperate?Comes from
Approvals, pending input, plan-readyNoSQL columns on the thread shell
Skip reasons, stop reason, budgetNofork-owned durable store
Deferred blockersYesraise_blocker

Two of the three sources exist whether or not the model plays along. A model that never calls raise_blocker still produces a correct console — it just has fewer rows. It degrades to "the loop is spent, and nothing is waiting on you", which is true and worth knowing, rather than to silence. That is the acceptance test, and it is why the prototype renders the empty state explicitly (scenario 2).

05 Direction C, in full

The Loops workspace

You raised this directly — "maybe can be a completely different workspace, which the users can toggle to and back into this current view." Here is what that is actually for.

It earns its place on one thing the thread-level console cannot do: answering across loops. At 9am with five loops, the question is not "what does this loop need" — it is "what does anything need", and then "which of these actually finished". A cross-loop inbox answers the first; a status list answers the second.

P3 Loops workspace The mode switch is top-left. Note the "Waiting on you" inbox spans every loop. Open standalone ↗

What to look at: the "Waiting on you" block aggregates items from every loop and marks which ones are blocking that loop versus merely raised. Below it, the loop rows put Spent and Done in deliberately different colours — see the note at the bottom of the prototype for why that distinction is load-bearing rather than cosmetic.

The honest risk

A mode you switch into is a mode you forget to check. Settings gets away with it because you go there on purpose; loops are the opposite — the whole point is that they happen while you are not thinking about them. The mitigation is that the switch itself carries an unread count, which is why it does in the prototype. If that count is ever wrong or stale, the workspace is worse than the pin.

06 Control

Settings — the on/off switch, and the ones that matter more

You asked for a toggle to turn the ability on and off. That is the top row. The rows under it are the ones I would argue about.

P4 Settings → Loops Toggle the master switch at the top to see the disabled state. Open standalone ↗

What to look at: "What a loop may do unattended". The first row — let the model schedule its own wake-ups — is not a new capability being added. It is a hole that is open right now.

Ship this row even if you ship nothing else

A full-access Claude thread today can arm up to 50 recurring jobs, re-firing for seven days, with no human in the path — because T3's canUseTool auto-allows everything in full-access and ScheduleWakeup self-permits. Turning it off means setting CLAUDE_CODE_DISABLE_CRON=1 in the environment the adapter already passes to the binary. That is zero upstream lines, and it closes a live hole independent of this entire feature.

The other decision on this page is the budget. Following the old design (and Devin, and OpenAI's platform, and GitHub Actions) there is deliberately no unlimited option — the route returns 400 rather than clamping, so a mistake is visible instead of silently corrected. And the display shows remaining, not just spent, because "4 check-ins left, ends 07:00" is a decision you can act on and "2 of 6" is trivia.

07 Vocabulary

Arming a loop, and every state it can be in

The vocabulary is the feature. The thing that failed on the original night was not that information was missing — it was that "it finished", "it ran out of rope" and "it died" all looked the same.

P5 Arming + 13 states Composer before/after at the top; the full state machine below. Open standalone ↗

What to look at: the tags under each state. Eight of thirteen states spend nothing. That is deliberate — almost everything that stops a loop firing is a good reason, and a design that burned a check-in on each would exhaust a six-check-in night without ever restarting the thread once.

Two switches stand between a thread and an unattended night, and no thread is ever armed implicitly. Auto-arming any thread with an active turn would have saved the original night with zero clicks — and is exactly how a token-burn incident happens.

08 Interaction

Loops, auto-resume, and running into limits

You flagged this specifically. Two schedulers that can both revive the same thread is a race, and the fork already owns one of them.

The rule: one owner per wake

A loop never nudges a thread with a pending auto-resume (guard 9). But that alone is not enough, and the reason is subtle: auto-resume only arms when its own per-thread switch is on. On a thread where you turned auto-resume off, a rate limit produces no pending resume, guard 9 passes, and the loop nudges straight into a live 5-hour limit.

So the loop runs a second fiber that taps the rate-limit event stream directly, reuses the fork's existing classifyRateLimit, and writes rateLimitedUntilMs to the durable store — durable, not in-memory, so it survives the restart that would otherwise reopen the hole. The event stream is PubSub-backed, so a second subscriber does not steal auto-resume's events.

Even if all of the above failed, a nudge rejected by a live limit produces no activity — so it takes a strike, and the loop stops after two. The failure mode is bounded by the strike detector regardless of whether the limit logic is correct.

09 Adjacent

Loops as maintainer bots

Issue #44 wants an agent that works a repo's issue queue. The question worth answering before building anything is whether that is a second feature or the same loop pointed somewhere else.

P6 Maintainer loop The comparison table at the top is the argument; the running view is below. Open standalone ↗

What to look at: the green rows in the comparison are everything that stays identical — trigger, reactor, budget, all fourteen guards, and the console. Only two things differ, and both are configuration.

It is the same loop. What changes is where work comes from (a label query instead of this thread's unfinished business) and when it ends (the query returns nothing instead of a done-file). Both are configuration.

The one thing it genuinely needs that an overnight loop does not is a work-source abstraction — something that answers "what should I do next" from outside the thread. That is worth designing once, now, rather than retrofitting later. Everything else that looks maintainer-specific (the queue panel, the never-merge rule, per-issue worktrees) is UI and policy.

The rule that makes it safe

A maintainer loop never merges and never closes an issue. Every output lands as a draft PR or a comment, and a human promotes it. Without that, the failure mode is a bot that quietly closes the issues it could not solve — and you would not find out for weeks.

Sequencing: #44 is a second work-source on a shipped loop, not a parallel build. It should follow, not accompany.

10 Machinery

The backend, in one page

Full version in docs/coil/loops-v2/BACKEND.md. This is the shape and the three decisions that carry the most weight.

Shape

A fork-owned reactor ticks once a minute. For each armed thread it reads one SQL projection column — updatedAt — and if the thread has been silent past its threshold and all fourteen guards pass, it dispatches an ordinary thread.turn.start, exactly as auto-resume already does in production. It mirrors apps/server/src/coil/autoResume/ file-for-file, because that module is proven and already reviewed.

Decision 1 — trigger on updatedAt, never on session.status

A background subagent's message auto-opens a synthetic turn that pins session.status = "running", and nothing closes it. Gating on it would deadlock permanently on exactly the threads this feature exists to save. Meanwhile thread.activity-appended rewrites updatedAt, so the predicate stayed quiet through all 1,358 orphaned activities on the original night and would have fired at ~01:07 instead of the human typing at 04:23. It reads a durable SQL column rather than a hot stream, which is why it is the only trigger that survives a mid-loop restart.

Decision 2 — reserve the attempt before dispatching

The budget is persisted before the dispatch, not after. This is the only unbounded path in the design: a provider that cannot spawn would otherwise tight-loop. Reserving first means it burns budget — six attempts, not 480 a night.

Decision 3 — durable JSON, not a migration

The migration registry is upstream-owned; adding to it buys permanent conflict surface for what one JSON file does fine. Every field carries a decoding default, because a missing required key fails the whole-file decode and the boot path turns that into an empty state — silently disarming every loop on the machine. That is the highest-severity footgun in the module and it has a dedicated test.

11 Negative space

Angles I considered and rejected

You asked for the ones that do not work and why. These are the ones I spent real time on before discarding.

Build on Claude's own cron / ScheduleWakeup

The most attractive option, because it might already work with zero code. Issue #42 established that the scheduler is compiled into the Claude platform binary, spread unconditionally into its tool registry, and constructed inside the non-interactive entrypoint the SDK uses — so a cron-fired turn plausibly reaches T3 today.

Four independent disqualifiers, any one of which is fatal:

ProblemDetail
Session-lifetime onlydurable crons are gated off, so it lives in an in-process table. The session reaper stops a binding after 30 minutes idle, and a pending wake is not an active turn. Delays clamp to [60, 3600]. Anything over ~30 min is dead on arrival — and nothing on disk records it was ever scheduled.
Remote gate, no overridethe wakeup tool's gate is code-default false, currently true only because a GrowthBook result was cached locally. No env escape hatch. And the fork relocates the config dir per provider instance — so the same build can have working loops on one instance and dead ones on another.
Claude-onlynothing equivalent under codex, cursor, grok, opencode. A dead affordance on four of five adapters.
Unboundedthe binary owns the table. You cannot cancel, cap, budget or audit what you cannot address.

What survives: the Stop hook exposes session_crons, which is the only way to know whether a thread will wake itself. Worth reading later as pure observability — to warn that a second scheduler is fighting ours. Phase 3, not load-bearing.

Arm on turn boundaries instead of an idle clock

Kills itself twice. Stopping a session emits a real turn.completed — so arming on it restarts exactly the work you just hit Stop on. And there is a branch that emits turn.completed with no turnId while still carrying cost, so any turnId-keyed denylist arms falsely. The denylist would also be hot-stream-only and therefore empty after every restart: it fails open.

An agent-authored JSON state contract

Rejected by the original panel and still rejected. It outsources the hardest judgement to the thing that just failed — the agent on the original night marked a turn complete with 33 minutes of work still running — and it degrades silently: an agent that stops honouring the schema goes quiet in a way indistinguishable from the bug. A one-line sentinel file with an mtime gate gets the same result for a fraction of the protocol surface.

Dollar-cost budgets

Tempting, and wrong for now. total_cost_usd is a field nothing in this repo has ever read, and the SDK's own documentation describes it as accumulated by the session — so summing it per turn would inflate quadratically and a "$25 cap" would trip around iteration 6 of a $4 run. A ledger whose entire selling point is trust cannot rest on an unverified number. Budget is check-ins and wall-clock until someone measures it.

A new command in packages/contracts

orchestration.ts is churn-12 and is upstream's pre-announced landing zone for its own scheduling concept. Zero contract edits means that when upstream ships automations, this feature becomes a caller rather than a migration.

Auto-arming any thread with an active turn

Would have saved the original night with zero clicks. Also exactly how a token-burn incident happens. Two switches stay.

The three I would write first

  1. Replay the original night. A turn completing at 00:19 with task.* activity until 00:52, then silence. Assert: no fire during the activity stream, exactly one fire at ~01:07. This is the acceptance test for the entire feature.
  2. The two question channels, side by side. One test where the agent calls AskUserQuestion at 01:00 (loop skips, spends nothing, console shows blocking) and one where it calls raise_blocker (turn continues, loop keeps firing, answer reaches the agent next check-in). Together they are the proof the split works.
  3. The empty console. A loop that ends spent with a model that never called raise_blocker. Assert the console still renders the stop reason and budget. This is the degradation test, and it is the one that stops this feature from repeating BATON's failure.
Deliberately not tested

The synthetic-turn-start marker on the wire. It is real, but it is a free-form optional string in a hot 3950-line file with no upstream test — a fork test asserting a fork-defined constant cannot detect upstream drift, so it would pass green while the feature silently broke. The design avoids depending on it at all; testing it would create the illusion of coverage.
