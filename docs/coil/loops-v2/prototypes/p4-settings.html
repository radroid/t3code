Loops

A loop keeps a thread working while you are away, and collects what it needs from you in one place.

Let threads run as loops
When this is off, no thread can be armed, nothing is scheduled, and the loop supervisor never starts. Existing loops stop at their next check-in.

Loops running at once
Ceiling across every project. Three loops at six check-ins is eighteen unattended turns a night.

What a loop may do unattended

Let the model schedule its own wake-ups
Claude can arm up to 50 recurring jobs by itself, re-firing for seven days, and in full-access it does not need your approval to do it. With this off, T3 is the only scheduler.
Answer its own approval prompts
Off means a loop that hits a permission prompt stops and puts it on your console instead of pushing past it.
Keep going through a usage limit
Hands the wake to auto-resume and spends no check-in while held. Turning this off ends the loop at the limit instead.
The first switch is open right now, with or without this feature. A full-access Claude thread can already arm its own crons — canUseTool auto-allows and ScheduleWakeup self-permits. Turning it off sets CLAUDE_CODE_DISABLE_CRON=1 in the environment the adapter already passes, which costs nothing upstream. This row is worth shipping even if nothing else here is.

How you find out

Push when a loop needs you
A question or approval it cannot get past. Uses the notifications you already set up.
Push when a loop stops
Finished, out of budget, or gave up. Says which — they are not the same thing.
Show loop check-ins in the transcript
Leaves a breadcrumb each time the loop restarts a thread, so a run is auditable after the fact.
