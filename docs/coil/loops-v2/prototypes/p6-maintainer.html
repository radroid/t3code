A maintainer loop — same primitive, different source of work

Issue #44 asks for an agent that works a repo's issue queue automatically. The question worth answering before building anything is whether that is a second feature or the same loop pointed at a different backlog. It is the same loop. Only two things change, and both of them are configuration.

Why this matters for sequencing. If a maintainer bot is the same reactor with a different backlog source and a different stop condition, then #44 is not a separate build — it is a second work-source adapter on top of a shipped loop, and it should be sequenced after the loop rather than beside it. The parts that look maintainer-specific — the queue panel, the never-merge rule, the per-issue worktree — are all configuration and UI, not new machinery. The one thing it genuinely needs that an overnight loop does not is a work-source abstraction: something that answers "what should I do next" from outside the thread. That is worth designing once, now, rather than retrofitting.
