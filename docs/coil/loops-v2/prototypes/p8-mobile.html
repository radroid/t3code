Loops on the phone

AGENTS.md requires a decision for web, desktop and mobile — and mobile is not a formality here. The phone is where you actually look at 4am, and it is the surface where "is it alive" and "does it need me" have to be answerable in one glance, without a sidebar.

1 · The list, and the console

Mobile has no persistent sidebar, so a loop cannot be marked by its position — it has to carry its state on the row. The same boxed-card treatment works; the progress ticks are what change, because on a phone the budget is the thing you cannot get to any other way.

Three push reasons only: it needs a decision, it stopped, it finished. Everything else is visible when you look, and pushing it would train you to ignore the two that matter.
The one thing mobile changes about the design. On web the sidebar can afford to say very little, because the console is one click away. On a phone the row is the summary — so the budget has to be on it, and "Spent" has to be legible without colour alone (it carries the word, not just the zinc dot). That is why the tick row exists at all: it started as a mobile requirement and turned out to be the clearest thing on the desktop card too.

None of this is in phases 0–5, and the row chrome is not free. Mobile surfacing and push are designed here and not built — no phase, no seam line, no acceptance criteria, no tests (PLAN §3 Out). And a budget on the mobile thread-list row is a mobile seam row, in a file the fork does not touch today; the report priced it at zero, which was wrong. Price it when mobile is built, not before.

Mobile also settles decision 1 in the report. Direction B — a bespoke "Loops" section in the sidebar — has no mobile equivalent, because mobile has no persistent sidebar to put it in. A loop-as-pinned-thread and a Loops tab both work on all three surfaces. That is not decisive on its own, but it removes B's only real advantage.
