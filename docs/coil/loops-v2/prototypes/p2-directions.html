Where does a loop live in the sidebar?

Same four threads, same two loops, three structural answers. The difference that matters is not how they look — it is what each one costs against upstream, because Sidebar.tsx is 3808 lines, is churned constantly, and the fork does not touch it today.

Direction A
A loop is a pinned thread
Arming a loop dispatches thread.pin. Upstream's pinned block already floats it above everything and stops it sinking into a shelf. The only loop-ness on the row is the arc glyph, which rides in the title.

Cheapest by a wide margin, and it is not a hack. A pin is a lifecycle transition, which is the one thing the sidebar's static-sort rule explicitly permits. The cost is that a loop is only distinguishable by a glyph — a stranger could not tell it from a pinned thread.
Direction B
Loops get their own section
A labelled group above Threads, with richer rows: progress against budget, the next check-in, and how many items are waiting on you — visible without opening anything.

Direction C
Loops are a mode you switch into
The sidebar keeps a two-up switch. Chat is today's shell, untouched. Loops replaces the list with loops and their run ledgers — the same move Settings already makes.

Cheaper than B and far more capable than A, because everything lives in fork-owned route files. The real cost is not seam, it is product: a mode you have to switch into is a mode you forget to check. Mitigated only if the switch carries an unread count, which is why it does above.
What the sidebar itself says about this. Sidebar.logic.ts carries an explicit rule: "static creation order… Activity NEVER reorders the list — a row holds its position from open until settled, so the screen only moves at lifecycle transitions." A loop that floats up because it is busy breaks that rule. A loop that pins does not, because pinning is a lifecycle transition. That single sentence is why A is idiomatic rather than a shortcut — and why any design that sorts loops by activity should be rejected outright.
