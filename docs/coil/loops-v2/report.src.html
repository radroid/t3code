0 The short version

What I would build, and what I would not

Recommendation

Build a durable, T3-native loop reactor that backstops the agent's own scheduler rather than replacing it — bounded by a mandatory check-in budget and a wall-clock deadline, with state on disk so a restart loses nothing. On a thread that is self-pacing happily it should fire almost never; how rarely it fires is the measure of a good implementation.

Make its user-facing surface a console, not a pill: when you open a loop you get a standing answer to "what do you need from me?", assembled from three independent sources so it stays useful even if the model never cooperates.

Ship a loop as a pinned thread (Direction A) — upstream already built pinning, so the sidebar costs nothing. Keep the Loops workspace (Direction C) as the upgrade for a later phase (PLAN Phase 6), once there is more than one loop to look at.

The one thing I would push back on

You asked for a questionnaire page. It is the right idea and it is the centrepiece of this report — but the obvious way to build it is a trap, and it is worth knowing before you pick. Claude's AskUserQuestion already produces exactly the structured questions you want, natively, today. It also blocks the turn until a human answers. An agent that hits a real fork in the road at 01:00 and asks about it correctly stops working until 09:00 — which is the precise failure you are trying to eliminate.

So the console needs two channels, not one: blocking questions (which genuinely stop the run) and deferred blockers (which do not). The distinction is not a technicality — it is the product. See §3.

01 The problem

What unattended work actually needs

Three things, and they have moved apart. One of them is now largely handled by machinery that already exists — which is what makes the other two worth building rather than re-litigating.

What it needs State today
1 · It keeps going
the agent picks work back up without you typing 		Largely working. Claude's own scheduler paces a session well within its range, and upstream's liveness tracking means a busy thread is now visible rather than silent. See §9.
2 · It stops on purpose, and you can tell why
finished vs out of budget vs died vs waiting 		Nothing does this. There is no budget, no deadline, no terminal vocabulary, and nothing that survives a restart to remember any of it.
3 · It collects what it needs from you
so a night isn't lost to one unanswered question 		Nothing does this either, and the one native mechanism that comes close (AskUserQuestion) halts the run while it waits. See §3.

2 and 3 are the feature. The framing matters because it changes what gets built: not a replacement scheduler, but the durable state, the bounds, and the collection surface that no scheduler provides.

The failure modes, in rough order of how often they bite

  1. You cannot tell a finished run from an exhausted one. The most common and the most boring. A run stops; the transcript ends; whether it got there or gave up takes five minutes of reading to establish. This is the one that costs you time every single morning, not once a quarter.
  2. One question eats the remaining hours. The agent hits a genuine fork, asks correctly, and waits. Nothing is broken, nothing looks broken, and the night is gone.
  3. Nothing bounds the spend. A loop with no deadline and no cap is a loop you have to be awake to stop.
  4. A restart loses the plot. Session-scoped state — including a pending self-paced wake — does not survive the app restarting, and leaves no trace that it ever existed.
  5. An outright stall. Real, and it is what originally motivated the issue, but the rarest of the five and the one most improved since.
The stall, for the record

The run behind issue #38 — thread 3a85bdd3, 31 turns — closed a turn at 00:19 while 1,358 background activities kept arriving for another 33 minutes, then went silent for 3h31m. It happened twice in one night, and every one of the eighteen user messages was a human asking whether it was still going.

It is a good illustration and a bad axis to design around. Upstream has since shipped ThreadBackgroundLiveness, which makes exactly this case visible in the sidebar, and the scheduler has improved besides. I over-weighted it in an earlier draft of this report. It belongs here as one exhibit, not as the reason for everything below.

What upstream fixed, and the shape of what is left

ThreadBackgroundLiveness maps the whole task.* lifecycle and surfaces it as a sidebar pill and a composer banner, so a busy-but-quiet thread reads as busy. Upstream #5677 went further and taught the session reaper to skip threads with live background work, so those sessions are no longer killed underneath you.

Both are presentation and preservation. Neither acts, neither bounds, and the liveness registry is explicitly in-memory — its own module doc says "no persistence, no migration. After a server restart the registry is empty."

So the residue is durability, bounds, and the question channel — which is a much smaller and much better-defined feature than "build a supervisor".

02 Re-measurement

Three things that moved under the old design

There is a 73k-word design at docs/coil/loop/DESIGN.md from a 4-design, 12-judgement panel. Most of it survives and I have reused it. Three of its load-bearing premises have expired.

1 · Upstream shipped pinning — two days after the design froze

da6e1a967 2026-08-04 feat(sidebar-v2): thread pinning for sidebar v2 (#5312) design frozen 2026-08-02 — two days earlier

pinnedAt is a real contract field. thread.pin / thread.unpin are dispatchable commands. There is a drag-reorderable pinned block that renders with no header. And the contract says outright: "A pin overrides the settled/snoozed lifecycle: while pinnedAt is set the thread renders in the pinned block and never classifies into a shelf." Read that narrowly: what a pin overrides is auto-settle. Snooze still outranks a pin — the sidebar's own partition loop says so, "'hide until Tuesday' temporarily suspends 'keep on top'. The pin survives underneath" — so a snoozed loop leaves the pinned block until it wakes, and comes back to its exact slot.

The old design spent considerable effort rejecting a sidebar rail — including a proposed document.querySelector portal it correctly called out as laundering hidden dependencies. That rejection was right, and it is now moot: the thing it was avoiding building already exists, reachable through a command instead of a DOM hack.

Consequence

"A distinct thread type that pins to the top of the sidebar" — issue #38's proposal 2 — is now mostly an upstream feature. Arming a loop can just dispatch thread.pin.

2 · The sidebar is not a seam row, and that cuts both ways

Sidebar.tsx (3911 lines) and Sidebar.logic.ts appear nowhere in SEAMS.md. The fork does not touch the sidebar at all today. So modelling a loop as a pinned thread costs zero — and giving it bespoke rendering opens a new row in one of the hottest files upstream owns.

The sidebar also states a rule that decides this:

Sidebar.logic.ts

"Sidebar sort: static creation order, newest thread on top. Activity NEVER reorders the list — a row holds its position from open until settled, so the screen only moves at lifecycle transitions."

A loop that floats to the top because it is busy breaks that rule. A loop that pins does not — pinning is a lifecycle transition. That single sentence is why Direction A is idiomatic rather than a shortcut, and why any design that sorts loops by activity should be rejected outright.

3 · The settings mount in the old design no longer exists

BetaSettingsPanel.tsx is gone. Today's settings surface is nine route files and a closed SettingsPath union in settingsSearch.ts that drives both the nav and search. The old design's "+2 lines, risk 6" costing is void, and re-pricing it is one of the open decisions in §14.

03 The centrepiece

The console — a standing answer to "what do you need from me?"

Your ask, restated: at any time I open the chat there should be a page where I have a questionnaire ready to be answered, or the things that are a blocker and the human is needed for. This is that page.

The old design's user surface was a pill — Loop watching · 12m, Loop 2/6 · ends 07:00. That answers "is it alive". It does not answer "what is it stuck on and what do you want from me", which is the question you actually have at 9am.

What to look at: the five scenarios along the top are the five ways a morning can go. Answering an option marks it resolved and — once the blocking ones are cleared — flips the loop back to Working, because answering is the resume. Note that "Stopped on these" and "Answer when you can" are visually distinct sections: that split is the whole design.

Why two channels, not one

AskUserQuestion is already a first-class concept. The Claude adapter intercepts it in canUseTool, emits a user-input.requested event carrying a structured payload, and the projection surfaces it as hasPendingUserInput — the indigo Awaiting Input you already see in the sidebar. The schema is exactly what a questionnaire needs:

UserInputQuestion = { id, header, question, options: [{ label, description }], multiSelect? } packages/contracts/src/providerRuntime.ts:444-464

And then, in the adapter:

// ClaudeAdapter.ts — AskUserQuestion interception in canUseTool const answers = yield* Deferred.await(answersDeferred); // blocks until a human answers
The trap

A loop and a blocking question are in direct tension, and no tuning resolves it. Nudge a thread parked on a real question and you push past the human's decision. Don't nudge it and one question costs the whole night. The guard table is right to refuse — which means the fix has to be a different channel, not a different threshold.

So: a fork-owned MCP tool, raise_blocker, that records a question and returns immediately. The agent parks that branch of work and carries on with something else; the answer is delivered on a later check-in. Blocking questions still exist and still block — but they become the exception rather than the only option.

Why this is not the mistake the old design already rejected

The old panel rejected an agent-authored contract (its "BATON" design) because it "outsources the hardest judgement to the thing that just failed" and "degrades silently". A questionnaire is that idea coming back through a different door, so it has to answer the same objection. It does, for one structural reason:

Console source Needs the model to cooperate? Comes from
Approvals, pending input, plan-ready No SQL columns on the thread shell
Skip reasons, stop reason, budget No fork-owned durable store
Deferred blockers Yes raise_blocker

Two of the three sources exist whether or not the model plays along. A model that never calls raise_blocker still produces a correct console — it just has fewer rows. It degrades to "the loop is spent, and nothing is waiting on you", which is true and worth knowing, rather than to silence. That is the acceptance test, and it is why the prototype renders the empty state explicitly — the "running, nothing needed" scenario.

Where the console renders — you said you were open to other ways

The content is settled. The placement is not, and the three answers have genuinely different consequences. The third one turns out not to be a loop feature at all.

What to look at: Shape C. Pending approvals and questions already pile up on threads you run by hand — a global "needs you" inbox surfaces all of them, and it is the only shape that keeps working if loops are switched off entirely. Loops become its heaviest contributor rather than its reason for existing.

A side effect worth banking

Pricing shape B answered an open question in your wayfinder queue. Issue #112 — "what does registering a right-panel tab actually cost?" — the answer is two seam rows: rightPanelStore.ts (the kind union, its list, and the tab factory) and RightPanelTabs.tsx (the actions array plus two switch cases). Neither file is in the ledger today. One qualification found on review: those two switches render the tab chrome. The panel's body comes from rightPanelContent's kind ternary in ChatView.tsx — an existing seam row, and a hot one (churn 83, risk 18094). Two rows holds only if the tab passes its content through children instead of opening a branch there.

My order: A, then C, then B only if you find yourself flipping tabs. A and C share their whole data layer — the same three sources, filtered differently — so C is nearly free once A exists. B is the only one that touches upstream files, and its advantage (reading while answering) shrinks once the console summarises what each check-in did.

04 Structure

Where a loop lives, and what each answer costs

Three structural answers, same data. The difference that matters is not how they look — it is what each costs against a fork that has to rebase onto upstream every day.

What to look at: the "seam cost" block under each column. A is free because upstream already built pinning. B is the most legible and the most expensive — it opens rows in two hot upstream files, one of which is where upstream keeps landing new shelf logic. C is in between, and its real cost is not seam at all.

Recommendation

A now, C later. Ship loops as pinned threads — it is free, it is idiomatic, and with two or three loops it is genuinely enough. Add the workspace when you have enough loops that a list beats a pin. Do not build B: it buys legibility you can get from C at a permanently higher rebase cost.

05 Direction C, in full

The Loops workspace

You raised this directly — "maybe can be a completely different workspace, which the users can toggle to and back into this current view." Here is what that is actually for.

It earns its place on one thing the thread-level console cannot do: answering across loops. At 9am with five loops, the question is not "what does this loop need" — it is "what does anything need", and then "which of these actually finished". A cross-loop inbox answers the first; a status list answers the second.

What to look at: the "Waiting on you" block aggregates items from every loop and marks which ones are blocking that loop versus merely raised. Below it, the loop rows put Spent and Done in deliberately different colours — see the note at the bottom of the prototype for why that distinction is load-bearing rather than cosmetic.

The honest risk

A mode you switch into is a mode you forget to check. Settings gets away with it because you go there on purpose; loops are the opposite — the whole point is that they happen while you are not thinking about them. The mitigation is that the switch itself carries an unread count, which is why it does in the prototype. If that count is ever wrong or stale, the workspace is worse than the pin.

06 The third surface

Loops on the phone

AGENTS.md requires a decision for web, desktop and mobile. Here it is not a formality — the phone is where you actually look at 4am, and it has no sidebar to lean on.

What to look at: the tick row on each list item. On the web the sidebar can afford to say very little because the console is one click away; on a phone the row is the summary, so the budget has to live on it.

Mobile settles decision 1

Direction B — a bespoke "Loops" section in the sidebar — has no mobile equivalent, because there is no persistent sidebar to put it in. Loop-as-pinned-thread and a Loops tab both work on all three surfaces. That is not decisive on its own, but it removes B's only real advantage over C.

Three push reasons, and a long list of things that must never push

It needs a decision · it stopped · it finished. That is all. A check-in firing is the loop working; a deferred blocker did not stop anything; a usage-limit hold resumes itself. Pushing any of them trains you to swipe away the two that matter — and the whole feature rests on you trusting the notification at 4am.

The push copy carries the distinction the whole design turns on: "ran out of rope — 4 of 7 alerts resolved, it did not finish" versus "finished, 9 of 9, stopped on its own with 3 check-ins unused". If you can only read one line on a lock screen, that is the line worth spending.

07 Control

Settings — the on/off switch, and the ones that matter more

You asked for a toggle to turn the ability on and off. That is the top row. The rows under it are the ones I would argue about.

What to look at: "What a loop may do unattended". The first row — let the model pace itself — is not a new capability being added, and it is not one being taken away. It is on today, you rely on it, and it stays on. What is new is that T3 can finally see what the model scheduled.

It is already on — the job is to see it

A full-access Claude thread today can arm up to 50 recurring jobs, re-firing for seven days, with no human in the path — canUseTool auto-allows in full-access and ScheduleWakeup self-permits. An earlier draft called that a hole to close. That was the wrong instinct: this capability works and you use it. The problem is not that the model can schedule — it is that T3 cannot see that it did.

So the fix is observability first: read session_crons, show pending wakes on the console, and let the loop stand down for as long as the agent has a wake pending inside the run's deadline (§9). The per-thread kill switch an earlier draft proposed — CLAUDE_CODE_DISABLE_CRON=1 through the environment the adapter already passes, to make T3 the only scheduler — is dropped (PLAN §3). Self-pacing is always on; T3 reads what the agent scheduled, stands by while a wake is pending inside the run's own deadline, and covers it when it does not land.

The other decision on this page is the budget. Following the old design (and Devin, and OpenAI's platform, and GitHub Actions) there is deliberately no unlimited option — the route returns 400 rather than clamping, so a mistake is visible instead of silently corrected. And the display shows remaining, not just spent, because "4 check-ins left, ends 07:00" is a decision you can act on and "2 of 6" is trivia.

08 Vocabulary

Arming a loop, and every state it can be in

The vocabulary is the feature, and it is the answer to failure mode 1 — the one that costs you time every morning. "It finished", "it ran out of rope" and "it died" must not look the same, because distinguishing them is most of what you actually do at 9am.

What to look at: the tags under each state. Nine of fifteen states spend nothing. That is deliberate — almost everything that stops a loop firing is a good reason, and a design that burned a check-in on each would exhaust a six-check-in night without ever restarting the thread once.

Two switches stand between a thread and an unattended night, and no thread is ever armed implicitly. Auto-arming any thread with an active turn would have saved the original night with zero clicks — and is exactly how a token-burn incident happens.

09 Interaction

Two schedulers, and where each one belongs

Claude's own scheduler works, and you have been using it. That is a correction to an earlier draft of this report, which treated it as unusable. The right answer is not to replace it — it is to know where its range ends.

What I got wrong, and what the numbers actually say

Issue #42's analysis was a static read taken on 2026-08-07, and I carried its conclusion forward without re-measuring. Two things it did not have:

gate cache, re-read today (~/.claude.json) tengu_kairos_cron true tengu_kairos_loop_dynamic true tengu_kairos_loop_prompt true ← new since that analysis tengu_kairos_cron_durable false ← still the real constraint upstream 2c7267ad4 — "stop the reaper from silently killing live background subagents" (#5677) ProviderSessionReaper now skips a binding when backgroundLiveness != null, not only when a turn is active.

So the reaper is materially less aggressive than that analysis assumed, and the scheduling gates are on. Put the numbers together and the practical range is clear:

Self-paced delay Outcome Why
≤ ~30 min works fires before the reaper's 30-minute idle threshold is even reached
30–60 min racy depends on the 5-minute sweep and whether background work kept the binding alive
> 60 min only through CronCreate ScheduleWakeup clamps delaySeconds to [60, 3600] — but that clamp is its own. CronCreate takes a five-field cron expression in local time, recurring for up to seven days, with no upper bound, and lands in the same session_crons table
across a restart lost silently cron_durable is false — the table is in-process, and nothing on disk records the wake existed

That explains both your experience and the original diagnosis. Self-pacing at a 20–30 minute cadence — which is the normal case, and what the tooling nudges you toward — lands squarely in the working band. The failures live at the edges: restarts, any provider that is not Claude, and — at the other end — a cron that names a time far past the night you were bounding.

The corrected position

T3 does not replace the Claude scheduler. It backstops and bounds it. The agent keeps pacing itself where it is good at that. T3 owns the things no in-process scheduler can do: survive a restart, enforce a budget and a deadline, collect questions, and say out loud whether a run finished or ran out.

Which means observability replaces the kill switch

If the agent is genuinely self-pacing, the worst thing T3 can do is fire its own check-in on top — two schedulers, doubled spend, and a confused agent. So the Stop hook's session_crons field stops being a nice-to-have and becomes load-bearing: it is the only way to know a thread has already scheduled itself.

That delivery is no longer an assumption — it is the single biggest one this design used to carry, and it has now been read out of the shipped binary (2.1.236). The { background_tasks, session_crons } payload is spread unconditionally into both the Stop and SubagentStop inputs; each entry arrives as { id, schedule, recurring, prompt }; and an empty table delivers [] rather than nothing at all. One undocumented edge came with it: prompt is truncated to 1000 characters, so nothing may depend on getting the agent's full instruction back. All of this is verified against a shipped dependency rather than against this tree, which means it can move without a repo diff — it is worth re-reading on an SDK bump.

The rule falls out of that, with one bound this report did not originally carry. While a recorded wake is pending and its next fire falls at or before the loop's own deadline, the loop does not fire until that wake is overdue by its grace: it waits, spends nothing, and the console says "self-pacing · next wake 02:35". The loop's own check-in becomes the fallback for when the agent has not scheduled itself, which is exactly the case the agent cannot handle: it has stopped.

The bound is new, and it is arguable

An earlier draft deferred to a pending wake at any distance, arguing that the [60, 3600] clamp bounded the exposure without a second rule. That argument is retracted. The clamp belongs to ScheduleWakeup alone, and the field the rule reads carries CronCreate entries too: a recorded 0 9 * * * would stand T3 down until 09:00, and a one-shot cron pinned to a future date would stand it down indefinitely. Capping deference at the loop's own deadline needs no new knob — past the deadline there is nothing left to defer to — but whether the deadline is the right cap, or whether this wants an explicit maxDeferMs, belongs beside decision 4 in §14.

The grace is derived from the recorded entry rather than fixed, because the scheduler jitters its own fires: "recurring tasks fire up to 10% of their period late (max 15 min); one-shot tasks landing on :00 or :30 fire up to 90 s early." Only the late half can manufacture a false "its wake didn't land", so a recurring entry gets max(90s, min(10% of period, 15min)) and a one-shot gets 90 s. A flat 90 s would report a healthy 30-minute cadence as lost every time it drifted three minutes — and on a healthy thread this reactor is supposed to be the thing that almost never fires.

I had this deferred to phase 3 as pure observability. It moves up: it is now part of the trigger. The cost is unchanged — a single spread of hooks into the existing queryOptions object in ClaudeAdapter.ts, with every line of logic fork-side.

And the third scheduler: auto-resume

The fork already owns one, so it is really three. The rule is the same one: one owner per wake.

A loop never nudges a thread with a pending auto-resume (guard 9). But that alone is not enough, and the reason is subtle: auto-resume only arms when its own per-thread switch is on. On a thread where you turned auto-resume off, a rate limit produces no pending resume, guard 9 passes, and the loop nudges straight into a live 5-hour limit.

So the loop runs a second fiber that taps the rate-limit event stream directly, reuses the fork's existing classifyRateLimit, and writes rateLimitedUntilMs to the durable store — durable, not in-memory, so it survives the restart that would otherwise reopen the hole. The event stream is PubSub-backed, so a second subscriber does not steal auto-resume's events.

Situation Who owns the wake Budget Console says
Agent scheduled itself, wake still pending the agent spends nothing Self-pacing · next wake 02:35
Agent scheduled itself, but the wake passed with no activity loop — the fallback spends one Its wake didn't land · check-in 3 of 6
Usage limit, auto-resume on auto-resume spends nothing Held — resumes 08:22
Usage limit, auto-resume off nobody — loop stands down spends nothing Held — limit until 08:22
Thread quiet, nothing scheduled loop spends one Check-in 3 of 6
Pending approval you spends nothing Paused — needs approval
You typed something you disarms, no reset Loop off — you took over

Row two is the one that earns the whole design. A self-paced wake that was armed and then did not land — because the session was stopped, the app restarted, or the gate flipped — is invisible today: there is no record it was ever scheduled. With session_crons persisted fork-side, T3 knows a wake was due, notices nothing happened, and covers it. That is the durability gap, stated precisely.

Belt and braces

Even if all of the above failed, a nudge rejected by a live limit produces no activity — so it takes a strike, and the loop stops after two. The failure mode is bounded by the strike detector regardless of whether the limit logic is correct.

10 Adjacent

Loops as maintainer bots

Issue #44 wants an agent that works a repo's issue queue. The question worth answering before building anything is whether that is a second feature or the same loop pointed somewhere else.

What to look at: the green rows in the comparison are everything that stays identical — trigger, reactor, budget, all fifteen guards, and the console. Only two things differ, and both are configuration.

It is the same loop. What changes is where work comes from (a label query instead of this thread's unfinished business) and when it ends (the query returns nothing instead of a done-file). Both are configuration.

The one thing it genuinely needs that an overnight loop does not is a work-source abstraction — something that answers "what should I do next" from outside the thread. That is worth designing once, now, rather than retrofitting later. Everything else that looks maintainer-specific (the queue panel, the never-merge rule, per-issue worktrees) is UI and policy.

The rule that makes it safe

A maintainer loop never merges and never closes an issue, and #44's v1 contract is tighter still: never full-access, always its own worktree and branch, and in v1 it never pushes and never opens a PR — every output lands as a plan or a comment, with draft PRs a later opt-in. A human promotes all of it. Without that, the failure mode is a bot that quietly closes the issues it could not solve — and you would not find out for weeks.

Sequencing: #44 is a second work-source on a shipped loop, not a parallel build. It should follow, not accompany.

11 Machinery

The backend, in one page

Full version in docs/coil/loops-v2/BACKEND.md. This is the shape and the three decisions that carry the most weight.

Shape

A fork-owned reactor ticks once a minute. For each armed thread it reads one SQL projection column — updatedAt — and if the thread has been silent past its threshold and all fifteen guards pass, it dispatches an ordinary thread.turn.start, exactly as auto-resume already does in production. It mirrors apps/server/src/coil/autoResume/ file-for-file, because that module is proven and already reviewed.

Decision 1 — trigger on updatedAt, never on session.status

A top-level assistant message arriving with no active turn auto-opens a synthetic turn that pins session.status = "running", and nothing closes it but a later SDK result, the next sendTurn, or the process exiting. Until one of those lands, nothing automated will: the session reaper skips any binding whose thread still has an activeTurnId. So a turn whose completion never arrives holds running indefinitely, and gating on session.status would deadlock on exactly the threads this feature exists to save. Meanwhile thread.activity-appended rewrites updatedAt, so the predicate stayed quiet through all 1,358 orphaned activities in the #38 run and would have fired at ~01:07. It reads a durable SQL column rather than a hot stream, which is why it is the only trigger that survives a mid-loop restart.

Two corrections to how this was argued before, neither of which moves the conclusion. It is not a subagent's message that opens the synthetic turn — upstream #5219 added a guard that returns first for any assistant snapshot carrying parent_tool_use_id, precisely to stop spawning one synthetic turn per subagent completion. And the #38 run is not evidence of a stuck synthetic turn: its post-turn traffic is system messages, which never reach that path. What survives is the reaper's rule, which is enough on its own.

Decision 2 — reserve the attempt before dispatching

The budget is persisted before the dispatch, not after. This is the only unbounded path in the design: a provider that cannot spawn would otherwise tight-loop. Reserving first means it burns budget — six attempts, not 480 a night.

Decision 3 — durable JSON, not a migration

The migration registry is upstream-owned; adding to it buys permanent conflict surface for what one JSON file does fine. Every field carries a decoding default, because a missing required key fails the whole-file decode and the boot path turns that into an empty state — silently disarming every loop on the machine. That is the highest-severity footgun in the module and it has a dedicated test.

12 Negative space

Angles I considered and rejected

You asked for the ones that do not work and why. These are the ones I spent real time on before discarding.

Replacing Claude's scheduler rather than composing with it

Corrected

An earlier draft of this report listed Claude's cron / ScheduleWakeup here as rejected outright, on "four independent disqualifiers". That was wrong, and it was wrong for a specific reason: it inherited issue #42's static analysis from 2026-08-07 without re-measuring. The gates are on, and upstream #5677 has since made the session reaper skip threads with live background work. See §9 for the numbers.

What is genuinely rejected is narrower: building the whole feature on it, and nothing else. Three constraints are real and re-verified today, and each one defines a job T3 has to do rather than a reason to dismiss the scheduler.

Constraint Still true? So T3 owns…
In-process only — cron_durable is false yes durability. A wake lost to a restart leaves no trace; T3's store is the trace.
ScheduleWakeup's delay clamps to [60, 3600] — but CronCreate's expression has no upper bound yes, and narrower than I first wrote anything longer than an hour on the one tool — and, on the other, the deadline that caps how long T3 will stand down for a cron it did not set.
Claude-only — no equivalent on codex, cursor, grok, opencode yes the other four adapters, which otherwise get nothing.
Gate is code-default false, true from a cached remote evaluation true, but on a visible degraded state rather than a loop that silently stops pacing.
T3 has no handle on the binary's table partly budget, cap and audit — but it can now read the table via session_crons.

What this changes in practice: the loop's check-in is a fallback, not the primary pacing mechanism. On a Claude thread that is self-pacing happily, T3 should fire almost never — and the measure of a good implementation is how rarely it needs to.

And what survives from the original point: the Stop hook exposes session_crons, which is the only way to know whether a thread will wake itself. I had that filed as phase-3 observability. Given the above it is phase 1 and load-bearing — it is what stops T3 firing on top of an agent that is already pacing itself.

Arm on turn boundaries instead of an idle clock

Stopping a session emits a real turn.completed — so arming on it restarts exactly the work you just hit Stop on. A turnId-keyed denylist is the obvious patch and it does not hold: it is hot-stream-only and therefore empty after every restart, so it fails open. (An earlier draft cited a second kill — a result branch emitting turn.completed with no turnId. Upstream #5710 removed that emission on 2026-08-08; the branch now emits only thread.token-usage plus a log line, so the argument rests on the two reasons above.)

An agent-authored JSON state contract

Rejected by the original panel and still rejected. It outsources the hardest judgement to the thing whose judgement you are trying to check — and it degrades silently: an agent that stops honouring the schema goes quiet in a way indistinguishable from the bug. A one-line sentinel file with an mtime gate gets the same result for a fraction of the protocol surface.

Dollar-cost budgets

Tempting, and wrong for now. The adapter stamps total_cost_usd onto turn.completed.totalCostUsd and nothing downstream aggregates it, while the SDK's own documentation describes the number as accumulated by the session — so summing it per turn could inflate quadratically and a "$25 cap" would trip around iteration 6 of a $4 run. Those semantics are unmeasured, and a ledger whose entire selling point is trust cannot rest on an unverified number. Budget is check-ins and wall-clock until someone measures it.

A new command in packages/contracts

orchestration.ts is churn-20 and is upstream's pre-announced landing zone for its own scheduling concept. Zero contract edits means that when upstream ships automations, this feature becomes a caller rather than a migration.

Auto-arming any thread with an active turn

Would have saved the original night with zero clicks. Also exactly how a token-burn incident happens. Two switches stay.

Considered, not rejected — deferred with a reason

These are live ideas that a first version should not carry. Listing them so you can see they were weighed rather than missed.

Idea Why not now
Scheduled loops — "start this every night at 23:00" Needs a thread-creation trigger, not just a thread-revival one, which is a second mechanism with its own failure modes. It is also exactly where upstream's automations work is heading. Ship revival first; a schedule is a wrapper around it later.
Reusable loop templates (Cursor Automations' shape — a saved definition with triggers and instructions) The right end state, and the prior art is strong. But a template is only worth it once you have run the same loop several times, and nobody has run one yet. Building the abstraction first would fix the wrong shape in place.
A loop that spans threads — one loop driving several worktrees at once This is what the maintainer loop looks like if you squint, and the work-source abstraction in §10 is the seam it would hang off. Deferred because concurrency across worktrees multiplies every failure mode at once, and the per-issue-thread shape gets most of the benefit.
Summarising each check-in so the ledger reads as prose rather than counts Cheap and appealing, and it is what would make the "Runs" tab genuinely readable. It costs an extra model call per check-in, against a budget whose whole selling point is that it is bounded and predictable. Worth doing once cost is metered, not before.
Letting the loop answer its own low-stakes questions Tempting for approvals like "read this file". But the moment a loop can answer for you, the console stops being a complete record of what needed a human — and that completeness is the only reason to trust it at 9am.

The four I would write first

  1. Self-paced, healthy. Agent schedules its own wake every 20 minutes for three hours. Assert T3 fires zero times and spends zero budget, while the deadline still applies. This is the regression test for "T3 does not fight the agent", and it is the one I would write before any other.
  2. Self-paced, wake lost to a restart. Agent schedules a wake for +25 min; the server restarts at +10 min. Assert the record survives, the unmet wake is noticed, and T3 covers it exactly once. This is the durability gap stated as a test — and it is the case that justifies the whole feature existing alongside a working scheduler.
  3. The empty console. A loop that ends spent with a model that never called raise_blocker. Assert the console still renders the stop reason and budget. This is the degradation property, and it is the one that stops this feature from repeating BATON's failure.
  4. spent is never reported as done. Budget or deadline exhausted with work left over must render as ran out of rope, never as success — the done-file is the only thing that says finished. This is failure mode 1 written as a test.
Deliberately not tested

The synthetic-turn-start marker on the wire. It is real, but it is a free-form optional string in a hot ~4.6k-line file with no upstream test — a fork test asserting a fork-defined constant cannot detect upstream drift, so it would pass green while the feature silently broke. The design avoids depending on it at all; testing it would create the illusion of coverage.

Re-verified against three more days of upstream

This report was written against merge-base 196c8ea0d. Before turning it into a plan I re-measured everything load-bearing against upstream/main at a4cc1367b — 116 commits, three days. The design holds. Three findings are worth carrying forward.

Still free

The beachhead is unclaimed: session_crons, ScheduleWakeup and CronCreate return zero hits across the server and contracts, options.hooks is still set nowhere in ClaudeAdapter (though the neighbourhood is no longer empty — #4466 sets settings: { disableAllHooks: true } on the capability probe), mcp/toolkits/ still holds only preview, and not one of the 116 commits mentions a loop, cron, schedule or automation. Pinning is fully intact, so Direction A still costs nothing.

A new failure mode — and it argues for raise_blocker

Upstream #5127 now settles pending user-inputs when a session stops, by resolving the deferred with an empty answer object. AskUserQuestion still blocks, so §3 stands. The agent does not carry on with a null decision: the handler unparks, the tool call is then denied — "User cancelled tool execution." — and the session is going away regardless. What survives is on the projection side. The runtime emits user-input.resolved carrying answers: {}, so hasPendingUserInput reads false afterwards and a voided question is indistinguishable from an answered one. A deferred blocker is durable fork-side state; a blocking question is in-memory. So the console cannot derive its list from hasPendingUserInput — it has to record the request when it is made, and mark it voided rather than answered.

Decision 3 is now priced, not estimated

Upstream shipped /settings/integrations three days ago (#7082) — a worked example of exactly the operation the Loops settings section needs. Reading what it paid: an own settings section costs the fork two new seam rows, settingsSearch.ts (~+13) and SettingsSidebarNav.tsx (+2), both additive, ~+15 lines total. The row count has not moved; the line count has. An earlier draft priced settingsSearch.ts at ~+4, which is about a third of the truth — each SETTINGS_SEARCH_ITEMS entry is a five-to-six line object literal, which is how upstream's own change to that same file came to +26. The fork renders its own panel from its own route and keeps state in coil-loop.json, so it pays neither of the two expensive rows upstream chose — SettingsPanels.tsx or the persisted contracts/settings.ts.
